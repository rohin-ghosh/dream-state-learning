## Exact remaining blockers

### R1. The single maximum synthetic store is unreachable

The inherited active-text path permits at most four deltas after each of 48
deployment programs: at most 192 total `ADD`, `REVISE`, `SUPERSEDE`, and
`LINK` operations. An `ADD` creates at most one live record with empty links;
each `LINK` later adds only one directed edge. Therefore any store constructed
from the stated empty/deployment-only reachable history must satisfy, even
before revisions or supersessions,

```text
number_of_created_live_records + number_of_committed_links <= 192.
```

Section 5 instead describes a shadow/retrieval view with 192 live records and
a link view with 64 links over 128 records. If these are one authentic store,
it needs at least `192 ADD + 64 LINK = 256` deltas and is impossible. If they
are two stores, the canary no longer exercises both diagnostics against the
same immutable terminal P1 store, and it constructs/embeds two stores whose
resources are not counted. The current wording “views” does not resolve that
fork.

Freeze one of two honest designs: use one reachable point on the 192-delta
frontier and acknowledge that it cannot simultaneously saturate record count
and link count; or define separate coordinate-wise stress fixtures, count both
store constructions, and combine their upper bounds conservatively rather
than calling them one scale-matched diagnostic root. Supply a model-free
transition trace proving every final record and link is reachable under the
exact `ACTIVE_TEXT_FIXED` law.

### R2. Raw-to-index canary embeddings are missing from every total

Confirmation overlay branches reuse the authentic frozen index and correctly
create zero new record embeddings. The canary explicitly starts from raw
synthetic events and times construction and verification of the store/index.
Every live record in that newly built dense index must therefore receive a
BGE document embedding; raw event blocks remain BM25-only.

For one 192-record store, that is 192 additional document embeddings/root,
1,536 over eight canaries, and at most 98,304 BGE document input tokens/root
under the inherited 512-token document limit. If R1 is resolved using separate
128- and 192-record stores, it is 320 document embeddings/root and 2,560 over
the canaries, with corresponding tokenization, embedding batches, index
inserts, memory, and time. V0 counts only 128 query embeddings and sixteen
query-embedding batches/root, so its canary and “all-in addendum” totals are
not all-in.

Choose the exact store design, then add document-embedding instances, input
tokens, batches, index construction/tokenization operations, and all 8- and
40-packet totals. Keep them distinct from query embeddings.

### R3. The maximum-token shadow fit is not constructively compatible with the fixed writer

The inherited 81,920 labeled and 655,360 attended figures are coordinate-wise
upper bounds: `320 positions * 256 labels` and
`320 positions * 2,048 attended tokens`. The terminal writer also requires 20
fixed anchor positions and exact authentic childhood, deployment, and
rehearsal suffix/conditioning bytes. V0 requires the canary corpus to attain
both maxima exactly, but supplies only a 48-program synthetic deployment
history and no construction proving that every fixed anchor and every one of
the 320 positions has exactly 256 labels and 2,048 attended tokens. Arbitrary
padding cannot repair this because padding is not fully attended, and changing
anchor/rehearsal/conditioning bytes would cease to exercise the ratified
writer.

Bind the complete synthetic childhood rows, fixed anchors, rehearsal fills,
and deployment rows and provide an exact tokenizer/model-free geometry proof.
If simultaneous equality is unreachable, run the exact fixed writer corpus
and report its actual maxima, plus a separately labeled trainer-load fixture
for coordinate-wise hardware stress. Do not describe a synthetic load-only
fit as the diagnostic shadow fit.

### R4. Canary checkpoint and process lifecycle is not single-valued

The link branch requires the authentic terminal P1 checkpoint, whereas the
shadow branch requires clean base plus the newly fitted shadow adapter. New
canary packets begin from synthetic public events and do not name a synthetic
P1 checkpoint, childhood checkpoint/rows, or adapter source. Section 2 also
says one root owns one inference process, while Section 6 refers to a distinct
shadow process. It is unclear whether P1 and shadow adapters are mounted
sequentially in one process, in two clean processes, or by a full process
restart; those choices change firewall risk, model-load time, peak memory,
cache state, and occupied GPU time.

Bind the canary's exact P1-like checkpoint/adapter and childhood inputs, the
number of processes, load/unload/reset order, adapter state hashes, cache
flushes, and which setup costs are inside the timed interval. The process law
must prevent either branch from inheriting the other's adapter or KV state.

### R5. The remaining p95/resource surface can still under-stress execution

The stopping-disabled 128-token actor workload is a legitimate inference
stress path, but one frozen “valid target-independent” compiler action is not
an upper bound on CompilerGym action latency or CPU/RSS across eligible
programs. The source also reports energy only when an undefined “stable”
counter exists and does not bind per-call latency measurement or disposition.
Finally, the claimed all-in table omits dense/BM25 operation totals,
clone/edge/block scans, optimizer steps/microbatches, file counts, and byte
ceilings already declared elsewhere.

Bind a prospective compiler stress/upper-bound law or explicitly exclude
compiler latency from the empirical lease estimator and reserve it by a
separate conservative bound. Define latency clocks and energy-counter
availability/calibration/missingness before canary execution. Print a complete
40-packet table (or an exact referenced formula table) for every hard-bounded
surface; “all-in” may not mean only calls, tokens, and fits.
