# One-parent/one-child strong-baseline closure audit v4

Date: 2026-09-06

Status: fresh independent read-only audit of the current proposal bytes after
the v3 repairs. This advisory changes no candidate byte and authorizes no
implementation, model/tokenizer call, benchmark generation, adapter operation,
external call, or GPU use.

## Verdict

**REVISE.** The v3 repairs close the literal calibration value, support-scope
precedence, process-block partition, scope-exception status, observation-count
wording, top-level malformed scoring, macro-F1 formula, and reusable-record
gold-set gaps. All resource arithmetic I recalculated is internally consistent,
and the exact one-parent/one-child topology remains intact. A deeper merger
counterexample now prevents closure: `ADD`, `REVISE`, `SUPERSEDE`, and `LINK`
are not mutually identified by the displayed evidence/store state, so several
certificate fixtures advertised as having one legal gold operation actually
admit two or more legal operations. The certificate also leaves two malformed
element/execution cases unallocated, and `SCOPE_EXCEPTION` erases the direction
of the exception it purports to store.

## Exact blockers

### 1. The merger does not make the certificate's gold operation single-valued

The certificate says every gold operation is single-valued by construction,
but its fixture conditions are stronger than the actual merger law:

- In a gold `REVISE` fixture, the current same-key record can legally be left
  untouched while the same replacement is emitted as `ADD`: `ADD` requires
  only a new hash-derived ID, null provenance, empty links, evidence, and a
  provisional/supported status. It does not forbid another live record with
  the same semantic key.
- In a gold `SUPERSEDE` fixture, the supported opposite proposition can likewise
  be emitted as `ADD`, because relation is not part of the semantic key and no
  same-key uniqueness rule exists.
- Conversely, general `REVISE` does not explicitly preserve the semantic key
  or require its target to be the displayed related same-key record. It can
  therefore mutate an unrelated live record into the evidence-derived record,
  subject only to ID/link/provenance preservation and its status transition.
- A `LINK` needs two live nonsuperseded records and exact hashes, but no public
  semantic predicate determines why they should be linked or in which
  direction. If both directed edges are absent, source-to-target and
  target-to-source are both legal. Thus a sealed LINK fixture cannot have a
  mechanically unique gold direction under the current contract.

This is not merely a scoring preference: `NOOP` legality is defined by whether
*any* legal delta exists, so an overpermissive operation relation changes live
behavior too. Bind the store invariant and operation choice in the merger and
the visible schema. At minimum, specify whether at most one live record may
exist per semantic key; require `ADD` only when none exists; bind exactly what
key/proposition identity `REVISE` preserves; bind the eligible old/replacement
relation for `SUPERSEDE`; and give `LINK` a public, directional, mechanically
derived eligibility predicate (or make linking a deterministic merger action
rather than a model-chosen delta). Then regenerate the certificate fixture
discriminators from those same laws.

### 2. One stored exception has two opposite meanings, and counter-scope
membership is not executable enough

For a fixed action family and local program, these two worlds produce the
same canonical proposition, guidance, memory type, scope, and semantic key:

```text
local VALID / external INVALID
local INVALID / external VALID
```

The same collision occurs for local-positive/external-negative versus the
reverse. Both become `EXCEPTION`, local `PROGRAM`, `CONTRADICTS`, `MIXED`, null
value, and `REVISE ... ON_CONTRADICTION`. Only opaque evidence IDs differ. The
record therefore fails to say which local behavior is the exception, cannot
render actionable direction to the actor, and permits incompatible live
same-key records. Add a mechanically derived basis and local/external bin (or
an equivalent lossless typed encoding) to the proposition/key/renderer.

For ordinary counterevidence, the phrase "use the same derived scope
variables" also lacks a membership function. Bind, for example, whether a
`PROGRAM` counter must be in the sole support program, whether every action in
a `PUBLIC_FEATURE` counter observation must contain every exact scope key, and
what program/feature condition a `CROSS_PROGRAM` counter must satisfy. The same
rule must apply to paired contrast and process counter groups. Without this,
two source-distinct mergers can accept different counter sets and derive
different statuses from identical bytes.

### 3. Certificate scoring and execution still have uncovered branches

The element scorer covers valid elements and invalid elements with *no*
uniquely legal class, but not an invalid element whose declared operation and
replacement status identify one class. A `LINK` with a bad hash or a
`REVISE_SUPPORTED` with one malformed provenance field is invalid yet has an
identifiable attempted class; the current branch assigns it neither to that
class nor to the fixture class. State one total rule for every invalid element,
including this case.

The once-only certificate is also called the "actual two-call updater" without
binding the executable dependency. It must say whether `CURATE` receives only
the model's immediately preceding accepted `REFLECT`, whether an invalid
`REFLECT` skips `CURATE` and charges a missing CURATE unit, and whether gold
REFLECT is ever used as CURATE input (it should not be if the gate measures the
actual pipeline). Finally, define that each sealed case starts from its own
presealed isolated temporary store and that reusable-record recall matches the
post-atomic-commit store for that case before aggregating distinct matches.
The present singular "final temporary store" otherwise permits a sequential
100-case interpretation with order-dependent IDs, links, and collisions.

After those bindings, retain the now-sound eight-class macro-F1 and
class-allocated top-level-malformed rules.

## Nonblocking notes

- The visible schema is now much closer to the merger than in v3. Any repair to
  the operation relation, exception encoding, or counter-scope rule must be
  copied into that source-bound file; repository-only repair would reopen the
  visibility blocker.
- The strong active-text comparator is fairly offered to every service in an
  isolated evolving store. `P1-R0` remains a full-package, unequal-training-
  compute comparison and the proposal correctly makes no equal-compute or
  named-method superiority claim. Parenting causality remains the registered
  P/U interaction, not that public figure.
- The proposal's later strength gates can falsify a weak updater, but a
  once-only empirical gate cannot resolve a nondeterministic legal contract.
  Close the merger relation before generating sealed certificate cases.
- The prompt schema's 8,118 bytes have not been tokenizer-measured in this
  proposal-only audit. The plan correctly reserves 4,096 fixed tokens and
  requires a later pinned-tokenizer receipt; overflow must remain a no-go, not
  an invitation to omit visible laws.

## Disposition

Do not promote `ACTIVE_TEXT_FIXED` as a validated strong baseline and do not
spend scientific roots from these bytes. Repair the operation relation first,
then the exception/counter-scope encoding and total certificate executor;
mirror every model-actionable law into the exact prompt schema; regenerate
source-bound hashes and prospective certificate fixtures; and obtain another
fresh independent approval. No change to the one-parent topology, public
P1-versus-R0 figure, registered estimands, root rule, or resource envelope is
required.
