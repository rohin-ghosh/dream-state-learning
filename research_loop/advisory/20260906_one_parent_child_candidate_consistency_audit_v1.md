## Verdict

**REWORK BEFORE EXTERNAL DELIBERATION.** The causal spine is strong and faithful
to Rohin's binding architecture, but the current bytes are not yet an exact,
resource-closed candidate. Four defects are blocking:

1. the childhood dose chosen by the proposal is an unexplained hybrid of two
   conflicting advisories (`J=3`, 12 parent decisions, 48 deployment programs);
2. the writer calibrates one or four target-token exposures and then mandates
   six exposures for scientific targets;
3. the unparented branch has no executable admission rule corresponding to the
   parented neutral-shadow rule; and
4. the hard call/token maximum assumes a DREAM cadence and neutral-shadow cost
   that the protocol does not bind.

The five-cell structure itself should be retained. Repair the exact protocol,
add this audit or its resolved dispositions to the deliberation context, then
issue a new workflow hash/export authorization. Do not implement or launch a
scientific run from the present candidate.

## 1. Fidelity to the binding architecture

### What passes

- The bundle explicitly forbids classrooms, cohorts, peers, teacher ensembles,
  population learning, and cross-child shared state.
- The treatment is one target-blind parent teaching one child process-level
  thinking through tasks. Independent roots are replications, not a classroom.
- The parent disappears before deployment by a proposed fresh-process deletion
  audit.
- The deployed learning system is the same child using `THINK`, `DREAM`, and
  `SLEEP`; the public comparison is `P1` versus raw frozen `R0`.
- The ordinary agent is not crippled: all five deployment services keep the
  same tools, skills, files, active textual/external memory, context limit,
  clock, token budget, task opportunities, and public outcomes.
- `THINK` is one continuous inference operation. Native tool calls are an
  output channel, not a separately learned actor.

### Required wording repair

One statistical root contains a parented child branch and a counterfactual
unparented sibling branch. That is scientifically necessary, but a literal
reader can object that the document calls this “one child.” State once,
explicitly:

> One treatment dyad contains exactly one parent and one parented child. The U
> branch is an isolated counterfactual child used only for causal estimation;
> it never observes or exchanges state with the dyad.

This preserves the user's one-parent/one-child mechanism without hiding the
replicated control child.

## 2. Causal correctness of `R0/U0/P0/U1/P1`

### The factorial is correct

The primary interaction

```text
D_r = [gAUC(P1)-gAUC(P0)] - [gAUC(U1)-gAUC(U0)]
```

correctly asks whether parenting changes the later marginal benefit of
deployment LoRA writes. `P0/P1` share exact parented childhood bytes and
`U0/U1` share exact unparented childhood bytes; deployment write permission is
the only within-pair switch. Giving U the same practice/write schedule is
necessary to avoid confounding parenting with nursery SFT. `R0` is correctly
retained as a fit-free raw reference and not mislabeled as U0.

The entry-adjusted trapezoidal formula is also correct for equal cuts:

```text
gAUC(c) = [2G(16) + 2G(32) + G(48)] / 6,  G(0)=0.
```

### Blocking defect C1: U admission is only asserted, not specified

Section 7 defines a positive parent-derived target by comparison with a
same-checkpoint neutral shadow. It never defines how U's self-reviewed
continuation becomes admitted. “Same public-world admission” is not executable:
U has no parent-selected lesson code, no specified prospective trigger, and no
named shadow/delta test. Consequently P and U could differ in both teaching and
the rule that decides which child outputs become gradient.

Repair:

- bind one treatment-independent absolute eligibility predicate for each
  target type (complete provenance, prospective process trigger, public
  support/utility guard, fresh homologous application, content firewall);
- apply that identical absolute rule to P and U;
- give both branches a same-checkpoint, same-budget neutral shadow or state why
  the shadow is only a P-specific causal diagnostic and is not part of target
  eligibility;
- make parent-relative improvement an **additional P attribution gate**, not a
  different basic definition of a learnable row; and
- specify how U chooses its process predicate without receiving a semantic
  lesson (for example, all prospectively registered predicates are evaluated
  offline after the child's neutral self-review).

Target-token and optimizer padding cannot repair a difference in semantic
admission.

### Defect C2: headline and causal contrasts need metric-qualified names

The claim ladder writes `U1>U0` and `P1>R0` without saying whether this means
entry value, terminal value, or gAUC. A parented checkpoint may start higher;
that is inherited competence, not lifetime learning. Bind distinct claims:

- `gAUC(U1)-gAUC(U0)>0`: unparented deployment-write efficacy;
- the registered `D>0`: parenting increased deployment-write benefit;
- a level curve or terminal contrast `V_P1(t)-V_R0(t)`: full-system value; and
- a gain contrast `gAUC(P1)-gAUC(R0)`: full-system learning over deployment.

The paper-facing `P1`/`R0` plot is descriptive for the whole developmental
package. It must not be presented as the causal estimate of parenting.

### Defect C3: spending rule dropped the mean-direction guard

The proposal advances when at least three of four pilot roots have positive
`D_r` and correctly rejects a `mean(D)>=0.05` efficacy threshold. The resource
advisory, however, requires both `3/4` positive **and mean D positive**. Without
the latter, three tiny positive roots and one catastrophic negative root pass.
Restore `mean(D)>0`; retain the prohibition on requiring `mean(D)>=0.05`.

## 3. Source-advisory conflicts were combined, not adjudicated

The normative proposal silently selects:

- `J=3` childhood fits from the transfer advisory;
- four opportunities per cycle, hence 12 parent decisions and 24 unique
  nursery tasks per branch, also from the transfer advisory;
- `E=48` deployment programs from the resource advisory; and
- a maximum confirmation size of 32, whereas the resource advisory offered a
  variance-triggered 48-root expansion.

The resource advisory instead budgets `J=4`, one parent decision per cycle,
two nursery tasks per cycle/path, and 48 deployment programs. The transfer
advisory proposes `J=3`, 12 decisions, and 64 deployment programs. These are
not cosmetic differences:

- the proposal triples adaptive parent interventions relative to the resource
  manifest (12 versus 4);
- it triples nursery task instances at J=3 relative to the resource pattern
  (48 across P/U versus 16 at J=4 in the resource manifest);
- it changes accepted target volume per fit and therefore writer dose;
- 48 versus 64 programs changes lifetime length and the ability to observe
  saturation; and
- removing the N=48 branch is a deadline/power decision.

Repair by adding a source-conflict disposition table to the proposal. For each
of `J`, opportunities/cycle, parent calls, nursery tasks, deployment programs,
and maximum confirmation N, state the two recommendations, the chosen byte,
and the scientific/resource reason. External deliberators may choose different
bytes, but they should not have to reverse-engineer a hybrid.

## 4. Writer dose and target-count closure

### Blocking defect W1: calibration does not cover the mandated dose

Section 10 calibrates exact complete supervised-target-token exposure in
`{1,4}`. Section 9 then says every admitted target receives six equal target
exposures in each childhood fit. The independent writer advisory says the
selected heat/dose must be frozen across authentic and control cells. Thus the
scientific writer operates outside its own calibration grid.

Repair one of two ways:

1. preferred: interpret scaffold frequencies as a distribution conditional on
   the selected total exposure and render exact integer counts only for a
   prospectively chosen common multiple; include that complete dose in the
   calibration grid; or
2. replace the six-row scaffold schedule with schedules whose total supervised
   exposure equals the selected `{1,4}` dose.

Do not describe six scaffold rows as one exposure: every repetition presents
the same target token to the optimizer and is an exposure for heat accounting.

### Blocking defect W2: cumulative target volume has no fit-bound proof

The proposal allows 12 opportunities and at least `THINK_TO_ACT` plus
`DREAM_STATE` target families, potentially from corrected source and fresh
application. It does not bind the maximum targets admitted per opportunity or
show that the cumulative final childhood rebuild fits the resource advisory's
128 optimizer-position, 262,144 attended-token, and 65,536 supervised-token
ceilings. At the permitted 512-token suffix maximum, even 24 targets replayed
six times can reach 73,728 supervised tokens before anchors; more than one
action/state target per source/application raises it further.

Repair by freezing:

- maximum eligible targets of each type per opportunity;
- whether earlier targets are replayed under the current sleep's fading mix;
- exact truncation prohibition and maximum target length;
- exact anchor target-token cost;
- deterministic selection when eligible rows exceed capacity; and
- a symbolic worst-case proof below every per-fit cap.

Selection cannot look at treatment success or downstream probe value. If all
eligible rows do not fit, the prospective selection key must be treatment-
neutral and frozen before outputs exist.

### Defect W3: “deterministic SLEEP” overstates the trainer contract

The zero-model admission/compiler can and should be deterministic. A GPU LoRA
fit is not bitwise deterministic merely because its seed is fixed unless the
backend and kernels guarantee it. Preserve Rohin's triad by saying:

> SLEEP contains no inference intelligence: deterministic provenance,
> admission, rendering, and transactional gates surround a seeded,
> receipt-bound LoRA optimization.

Either enforce deterministic algorithms and bind the tensor hash, or specify a
frozen reproducibility tolerance. Do not make a stronger determinism claim
than the implementation can test.

## 5. DREAM and the Think–Dream–Sleep triad

### What passes

- DREAM uses the same child model and the same active LoRA. There is no learned
  dreamer, planner, curator, verifier, or sleeper module.
- The harness fixes only trigger, immutable state, schema, provenance, and
  safety gates; the child chooses the narrative successor. Successful
  `DREAM_STATE` responses are later response-only targets, so context
  management can actually improve through the one LoRA.
- Old traces remain in the append-only ledger and recall handles are tested
  before dropping context, making reconciliation reversible.
- SLEEP makes zero language-model calls and writes only child-originated native
  targets. This correctly preserves “THINK is loop; DREAM reconciles context;
  SLEEP is write.”

### Blocking defect D1: DREAM cadence is open but the budget is hard

The child may request `RECONCILE_CONTEXT` early, and a pressure threshold also
forces it. No maximum is specified. Yet the resource ceiling counts exactly
one nursery dream per opportunity and exactly one deployment dream per
write-era/cell (including three for R0). An agent that requests more dreams can
exceed 4,811 calls; rejecting its requests changes the learned context policy.

Repair by binding one of:

- a total generated-token budget in which DREAM calls consume the same task
  allocation and a hard per-task/per-era maximum; or
- an exact maximum count, with early requests replacing rather than adding to
  the scheduled dream.

State precisely whether a failed DREAM consumes the opportunity, how many
retries exist (prefer zero), and whether emergency truncation terminates the
task or continues under an invalid-context flag.

### Blocking defect D2: syntactic successor validity is weaker than usefulness

The proposal validates restoration and one legal post-reset action. A legal
action can still demonstrate that the successor discarded causally important
state. The writer advisory required a registered world-supported continuation
before the DREAM target became eligible. Restore that gate: a `DREAM_STATE`
may enter SLEEP only after the post-reset continuation clears a prospective
process predicate plus same-budget utility/non-inferiority rule. Schema and
legal action alone are engineering checks, not evidence of useful context
management.

### Defect D3: semantic firewall could become hidden SLEEP intelligence

Section 7 requires an “independent semantic” content firewall for every parent,
restatement, and target but does not name its implementation or resource cost.
A reviewing LLM that decides which rows train is a learned curator inside
SLEEP, contradicting the zero-model deterministic compiler. Bind the live
firewall as a deterministic closed-schema/capability/lexical rule. Use blinded
human or independent-model semantic laundering review only on the frozen
parent policy and development fixtures before scientific traces exist; it may
not make per-row admission decisions. If a per-row semantic model is retained,
declare it as another intelligence, freeze it, budget it, and weaken the triad
claim.

## 6. Arithmetic audit

### Fits: correct under `J=3`, `K=3`

```text
childhood P/U: 2*3 = 6 fits/root
deployment P1/U1: 2*3 = 6 fits/root
total: 12 fits/root; R0/P0/U0 add zero fits

writer/heat canary maximum: 21 fits
N=20: 21 + 12*(2+4+20) = 333
N=32: 21 + 12*(2+4+32) = 477
```

These proposal totals are arithmetically correct. They intentionally differ
from the resource advisory's `J=4` totals of 383/551.

### Calls/tokens: numerically reproducible only under unstated assumptions

The advertised 4,811 calls and 757,504 output tokens equal this implicit
manifest:

| class | instances | calls/instance | calls | output tokens |
|---|---:|---:|---:|---:|
| P/U nursery source+application tasks | `2*3*4*2=48` | 12 | 576 | 73,728 |
| P/U review/restatement | 24 | 1 | 24 | 4,608 |
| P/U nursery DREAM | 24 | 1 | 24 | 9,216 |
| P parent correction | 12 | 1 | 12 | 3,072 |
| five-cell deployment wake | `5*48=240` | 12 | 2,880 | 491,520 |
| five-cell deployment DREAM | `5*3=15` | 1 | 15 | 11,520 |
| five-cell probes | `5*4*8=160` | 8 | 1,280 | 163,840 |
| **total** | | | **4,811** | **757,504** |

The aggregate multiplication is correct:

```text
26 roots: 125,086 calls; 19,695,104 output tokens
38 roots: 182,818 calls; 28,785,152 output tokens
```

But this table is absent from the proposal, and its assumptions conflict with
the free DREAM trigger. It also does not say whether neutral-shadow generation
fits inside the 12 calls/1,536 tokens of each P source task. If it is additional,
the hard maximum is understated. Add the table, split source/corrected/shadow/
application allocations, and account for headroom/saturation calibration,
semantic audits, and development-only model calls separately from root cost.

## 7. Workflow, context, and scope sufficiency

### Mechanical checks that pass

  consensus; they cannot ratify or implement.

### Blocking workflow defect F1: the external-export approval hash does not
bind source bytes

The workflow hash binds only the JSON list of paths, not the current contents
of those paths. Source hashes are created when deliberation initializes, after
approval. Therefore an approval sentence citing only the workflow SHA does not
cryptographically authorize exact directive/context bytes if any source changes
between approval and initialization.

Repair by generating a proposal-only source-binding manifest containing the
directive plus every context path/hash, bind that manifest (or its aggregate
hash) in the approval sentence, and make initialization verify it. At minimum,
initialize locally immediately before approval, present the resulting
`source_bindings` digest, and reject any later mismatch. The later consensus
ratification already has stronger exact-byte bindings; export authorization
should not be weaker.

### Blocking scope defect F2: “external service” also forbids deliberation

The forbidden scope says no one may “access an external service” before later
ratification. The proposed five-role deliberation itself calls external OpenAI
Codex providers before that ratification. A separate conversational approval
can authorize it, but the scope bytes given to deliberators contradict the
workflow. Repair the clause to exempt only the separately exact-authorized,
proposal-only architecture-deliberation providers while continuing to forbid
scientific parent/child/evaluator/trainer/runtime services.
