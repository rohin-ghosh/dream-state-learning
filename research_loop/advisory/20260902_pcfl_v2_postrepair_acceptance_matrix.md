# PCFL-Compose v2 post-repair acceptance matrix

**Status:** advisory validator checklist only.  It identifies (a) the exact
normative contracts and fixture definitions a repair author must bind before
asking for another intake and (b) the executed receipts that a separately
ratified implementation must bind before the pre-GPU gate.  It does not
approve the reviewed bundle, implementation, an intake transition, or a run.

**Reviewed proposal:** `2fc2521d821efc2ff4852ef9decbb4c2bdf834a8f1b0ff438aec7e78d2a0f047`.
The three pre-intake audits agree that its 3,414-scientific-call / 3,416-process
opportunity arithmetic is correct, but that the listed contracts cannot yet
enforce the protocol.  Every normative rule, schema constraint, scientifically
material fixture dimension/mutation, expected decision, and failure behavior
below must be present in the *next*, rehash-bound proposal.  Executed fixture
objects, incidental schema-witness literals, reducer traces, count
certificates, and validation receipts are deliberately **not** required before
intake: `AGENTS.md` requires exact human ratification before implementation or
tests.  Those executable artifacts are mandatory after ratification and before
T17/pre-GPU approval, under the exact boundary in
`20260902_pcfl_v2_fixture_authority_adjudication.md`.  A future implementation
cannot choose a scientific value or close a proposal-level semantic omission,
and a prose-only fixture class cannot later substitute for an executed receipt.

## Required closure order and authority boundary

P1--P7 are protocol prerequisites; P8--P12 are scientific/analysis
prerequisites; P13--P14 are preservation checks.  A proposal is not ready for
intake if a fixture's scientifically material input dimensions, mutation class,
expected result, or failure behavior is left to the future implementer, if a
future executable bundle is expected to choose an allowed scientific value,
or if fixing a schema changes roster/token/CPU arithmetic without regenerating
the normative P10/P14 count contract. Exact incidental witness bytes that
cannot reach a model or scientific assignment belong to the post-ratification,
pre-GPU fixture catalog instead.

The authority sequence is exact and non-circular:

1. **Pre-intake proposal:** freeze schemas, algorithms, visibility, resource
   limits, complete fixture definitions, expected results, and claim limits.
2. **Deliberation and human ratification:** approve those exact bytes and only
   the declared implementation/CPU-test scope.
3. **Stage 0 implementation:** materialize the frozen fixtures and produce
   schema/reducer/generator/count/lint receipts without changing scientific
   semantics.  Any necessary semantic change returns to a new intake.
4. **T17/pre-GPU:** rehash code, executable dependencies, all P1--P14 receipts,
   and fresh review.  Missing or failing evidence is `NOT_RUN`, never waived.

Thus a merely described *underspecified* fixture is not proposal closure, while
an unexecuted but total, exact fixture contract is the most evidence the
pre-ratification authority state is permitted to contain.

## Audit reconciliation

There is no substantive conflict among the three audits.  All retain the exact
3,414/3,416 ceiling and the narrow DEV framing, accept the supplied extractor
only as event-local perception scaffolding, and reject opaque semantic scoring
and h-mediated-action language.  The science audit identifies three central
causal blockers; the contract and adversarial audits expose their additional
runtime, information-flow, resource, and reporting preconditions.  That is a
difference in granularity, not a disagreement.  The only conditional choice is
whether to define a mechanical branch-responsive selection predicate (then use
the carefully nonsemantic word “revision”) or narrow the descriptor to B
commitment response; either is valid only after P1--P8 are frozen and tested.
