## Ruling

The authority repair should **not create a FeltCraft-to-PCFL runtime
dependency**. The current FeltCraft V7 functions are byte-frozen and useful as
design evidence, but none is isomorphic to the proposed PCFL M0 semantics.
Importing them would add an authority and oracle boundary without eliminating
any PCFL implementation.

Therefore the exact primitive mapping is a **zero-runtime-reuse mapping**:

- all five V7 files remain unchanged, terminal, and outside the PCFL runtime;
- PCFL may cite their hashes and the negative lessons of their audit in
  governance-only source artifacts;
- PCFL code, materializers, checkers, fixtures, tests, actor views, and later
  M-TEXT packages may not import, invoke, read, copy, translate, or consume a
  V7 function, output, oracle, golden, receipt, or audit value;
- any future proposal that redesigns PCFL to use an actually isomorphic V7
  primitive must name that primitive and seek a new exact human scope decision.

This closes the current V7 authority problem rather than postponing it. The
proposed `E-V7-TO-M0-REUSE` edge is deleted. A governance-only citation edge is
not a runtime edge and transfers no bytes, behavior, permission, or scientific
meaning.

The durability repair is a two-freeze protocol:

1. exact preparation **source** is separately ratified for a no-selection,
   CPU-only materialization attempt;
2. the independently checked output is then frozen by a second exact human
   decision before it can become M0 implementation input.

That is the only practical resolution of the current circular requirement that
materialized bytes exist before any operation capable of materializing them.
It requires Rohin to explicitly select this narrow exception to the current
`D-EXACT-BYTES` disposition. It does not weaken the rule that no generated byte
can reach M0 or M-TEXT before the second freeze.

## Oracle firewall

The firewall is deny-by-construction rather than “trusted not to look.”

1. **No dependency:** PCFL materializer, independent checkers, M0 runtime, M0
   tests, fixture objects, and M-TEXT handoff contain no import, subprocess,
   file-read, symlink, package-resource, reflection, callback, environment,
   configuration, or serialized-object edge to V7.
2. **No copied oracle:** V7’s 72 positive vectors, 25 negative fixtures,
   fixed twins, expected costs, golden report bytes, receipts, mismatch state,
   and `scope_audit.json` values cannot enter PCFL source, fixtures, tests,
   actor-visible state, or later model-visible bytes.
3. **PCFL-local ground truth:** every PCFL expected value is derived from the
   separately ratified PCFL semantic specification or an independently
   authored PCFL oracle. A matching number such as a path cost is insufficient
   to create a V7 provenance edge.
4. **Actor denial:** V7 path names, hashes, protocol IDs, role/descriptors,
   error codes, source bytes, and result bytes never appear in `FiniteView`, a
   reader return, carrier row, prompt projection, tool envelope, filename,
   error, timing surface, session state, or receipt visible to an actor/model.
5. **Mutation test:** inserting any V7 import, path read, hash-derived actor
   field, report byte, expected vector, or oracle call must make preflight fail
   before materialization or M0 execution.

Because no V7 runtime byte is reused, the existing failed V7 scope audit does
not need to be “fixed” to construct PCFL. It remains negative evidence and
cannot be presented as passed, superseded, inherited, or repaired by PCFL.

If Rohin instead chooses actual V7 runtime reuse, this zero-reuse ruling must
be replaced by a new deliberated change that: (a) changes PCFL semantics so a
named primitive is exactly isomorphic; (b) binds its exact inputs, outputs,
and compatibility vectors; (c) grants explicit PCFL successor authority over
the named source bytes; (d) performs a new PCFL-specific independent semantic
source review and human adjudication; and (e) preserves all oracle denials.
The old V7 audit cannot satisfy that review.

## Canonical encodings and identities

All governance manifests and receipts use RFC 8785 JCS UTF-8 bytes plus
exactly one LF. Artifact payload bytes retain the encoding specified by the
ratified PCFL semantic schema. Paths are repository-relative NFC UTF-8 with no
empty, absolute, `.`, `..`, NUL, or backslash segment and no symlink traversal.

For a sorted manifest row `(path,size,digest_raw32)`, encode:

```text
uint32be(len(path_utf8)) || path_utf8 || uint64be(size) || digest_raw32
```

The manifest root is:

```text
SHA256("PCFL-M0-MANIFEST-v1\0" || concatenated_rows_in_raw_UTF8_path_order)
```

The preparation input root binds, in fixed field order:

```text
semantic_spec_root
transition_table_sha256
failure_precedence_sha256
object_schema_manifest_root
materializer_source_root
constructive_checker_source_root
axiomatic_checker_source_root
runtime_manifest_root
scope_proposal_sha256
consensus_sha256
human_preparation_ratification_sha256
```

`run-id` is the lowercase hex digest:

```text
SHA256("PCFL-M0-RUN-v1\0" || preparation_input_root_raw32)
```

Thus two invocations over identical authority and source bytes have the same
run identity. An operational retry receives the next four-digit attempt
ordinal under the same `run-id`; it is not a new run, root, datum, or unit.

`freeze-id` is:

```text
SHA256("PCFL-M0-FREEZE-v1\0" || preparation_input_root_raw32
       || output_manifest_root_raw32
       || constructive_checker_receipt_sha256_raw32
       || axiomatic_checker_receipt_sha256_raw32)
```

No timestamp, hostname, process ID, username, wall time, attempt count, or
unordered filesystem enumeration enters these identities.

## Independent checker lineage

“Independent” is operationally bound; agreement is not called semantic proof.

### Constructive checker

- authored in a fresh context by an identity different from the materializer
  author;
- sees the ratified semantic specification and schemas but not materializer
  source or candidate output during authorship;
- independently constructs every root/object/transition using a different
  control decomposition;
- imports no materializer/local helper module;
- receives candidate bytes only after its own source hash is frozen.

### Axiomatic checker

- authored in another fresh context by an identity different from both prior
  authors;
- sees the ratified semantic specification, closed invariant list, and schema
  definitions, but neither prior source implementation nor candidate output
  during authorship;
- checks exhaustive algebraic invariants, cardinalities, prefix collisions,
  transformation locality, provenance cases, reducer completeness, and bound
  mutation fixtures rather than regenerating through the materializer’s
  algorithm;
- imports no code from either prior path and shares only standard-library
  primitives and the frozen schemas;
- receives candidate bytes only after its source hash is frozen.

The two checker receipts must name their author/context identities, source
roots, allowed imports, exact input root, exact candidate manifest root, every
test outcome, and output digest. Agreement proves deterministic reproduction
and independently checked invariants. A fresh semantic reviewer must still
inspect exact frozen source and fixture bytes before M0 acceptance; neither
checker nor its receipt is scientific evidence.

## Materializer, manifest, and freeze order

The exact order is non-negotiable once Option B below is human-approved:

1. **Source freeze:** hash-bind the complete semantic specification, closed
   transition/failure tables, schemas, materializer, both checkers, runtime,
   authority scope, consensus, and preparation ratification. No fixture output
   exists yet.
2. **Preflight:** verify every input byte/hash/path, import/capability denylist,
   exact runtime identity, output limits, and empty authoritative destination.
   Emit a nonauthoritative preflight receipt in staging.
3. **Materialize once:** produce the complete finite universe without RNG,
   search, ranking, selection, favorable-root filtering, retry/replacement of
   individual roots, model/tokenizer use, or result feedback. A suite failure
   is output, not a reason to choose another root.
4. **Install candidate objects:** atomically install only content-addressed raw
   objects and one candidate manifest. Candidate installation grants no use.
5. **Constructive check:** run against exactly the candidate manifest.
6. **Axiomatic check:** run independently against exactly the same manifest.
7. **Postflight:** recompute all source/runtime/authority hashes and require
   exact equality with preflight. Any change fails the run.
8. **Candidate receipt:** create one immutable receipt for `run-id`. It records
   pass/fail and all digests. Failure receipts are durable and cannot be
   replaced by a favorable attempt under the same input root.
9. **Fresh review:** independently review exact source, exact candidate bytes,
   checker lineage, oracle firewall, and failures. Review cannot edit them.
10. **Human fixture freeze:** Rohin explicitly ratifies the exact candidate
    receipt, manifest root, review bytes, scope, and paused state. Only this
    transition creates `frozen/<freeze-id>.json` and
    `human_fixture_freeze.json`.
11. **M0 implementation gate:** a separate change may authorize M0 source to
    consume exactly that `freeze-id`. M0 cannot enumerate other candidates.
12. **CPU conformance and review:** implementation-generated receipts occur
    after implementation and before any model-facing use.
13. **M0 nonclaim acceptance:** human governance may accept only software
    conformance. It does not unlock M-TEXT.
14. **M-TEXT package:** separately bind rendering, tokenizer/chat template,
    parser/tool envelopes, full session state, reset sole channel, clean guard,
    DEV/reserve/confirmation, resource factors, endpoints, and claim rules.

No stage automatically promotes the next. A hash match is necessary but never
sufficient authority.

## Atomic install, freeze, and promotion

The future implementation must use a content-addressed, no-overwrite protocol:

1. write each candidate byte sequence to a same-filesystem staging file opened
   exclusively; close and `fsync` the file;
2. recompute size and SHA-256 from the closed staged file;
3. install the object at its canonical content-addressed path with a
   no-replace atomic link/create operation; if it already exists, require exact
   byte equality or fail `OBJECT_COLLISION`;
4. `fsync` containing directories;
5. build the canonical manifest only from installed object hashes, write/fsync
   it in staging, then install it no-replace at its digest-named path;
6. checkers read objects only through the installed manifest and operate with
   write access only to their own staging receipt;
7. install the final `run-id` receipt no-replace; an existing byte-identical
   receipt returns `DUPLICATE_COMPLETE`, while any different receipt at the
   same identity fails `RUN_ID_COLLISION`;
8. human freeze and later software promotion are single canonical JCS+LF
   reference objects installed no-replace. They move no fixture bytes and name
   exact upstream hashes.

There is no mutable `latest`, `passed`, `current`, or symlink pointer. A
promotion is an immutable reference receipt, not a file move or overwrite.

## Crash recovery and duplicate runs

- Only installed content-addressed objects, manifests, run receipts, and human
  freeze references are authoritative.
- A crash before a run receipt leaves nonauthoritative staging. On restart,
  recompute `run-id`; if an exact receipt exists, verify it and stop as
  `DUPLICATE_COMPLETE`.
- If no receipt exists, create the next unused attempt directory under the
  same `run-id`, reuse only verified content-addressed objects, and recompute
  the full manifest. Never adopt a partial staging manifest.
- Stale staging is ignored or quarantined; it is never deleted as part of a
  scientific/authority decision and never counted as another attempt in an
  estimator.
- A failed complete receipt is terminal for that preparation input root.
  Repair requires changed source/spec/authority bytes, hence a new input root
  and `run-id`; the prior failure remains present.
- If both a receipt and stray staging exist, the receipt wins only after all
  of its hashes verify. Otherwise fail closed; do not regenerate over it.
- No crash, timeout, malformed output, or resource exhaustion permits
  root-level retry, replacement, omission, or favorable selection.

## Pre/post hashes, output limits, and malformed precedence

The preflight receipt records exact SHA-256 and size for every source,
specification, schema, authority, runtime, and permitted dependency byte plus
the aggregate preparation input root. It also records that all authoritative
candidate/freeze destinations are absent or byte-identical CAS objects.

Postflight recomputes the same rows and input root, records the output manifest
root and both checker receipt hashes, and requires pre/post identity. It may
record wall time diagnostically, but timing cannot affect acceptance.

Exact proposed limits for this small finite CPU fixture are:

- one raw object: at most `1,048,576` bytes;
- complete installed object payload: at most `67,108,864` bytes;
- one manifest or receipt: at most `1,048,576` bytes;
- one staging attempt including logs: at most `134,217,728` bytes;
- captured stdout and stderr: at most `4,194,304` bytes each;
- path count: at most `16,384` objects;
- path length: at most `512` UTF-8 bytes.

Exceeding a limit fails the complete run; it never truncates an authoritative
object.

Malformed input/receipt precedence is exactly:

1. `PATH_OR_TYPE` — absent, nonregular, symlinked, foreign, or illegal path;
2. `SIZE_LIMIT` — byte/path/count limit exceeded;
3. `ENCODING` — invalid UTF-8/NFC or canonical-byte failure where applicable;
4. `SCHEMA` — missing/extra/duplicate/mistyped/out-of-domain field;
5. `BINDING` — path, authority, runtime, pre/post, or SHA mismatch;
6. `SET_IDENTITY` — missing, duplicate, foreign, or reordered required row;
7. `ORACLE_FIREWALL` — forbidden dependency, import, copied constant, or read;
8. `CHECKER_DISAGREEMENT` — checker root/result mismatch;
9. `SEMANTIC_TEST` — an exact invariant or mutation test fails;
10. `INCOMPLETE` — crash, timeout, or missing finalization after all prior
    parsable checks.

Return only the first applicable code. A malformed or failed receipt is never
promoted and never converted to an adverse scientific zero; it is software
failure evidence.
