# One-parent/one-child strong-baseline counter-audit v1

Date: 2026-09-06

Status: **fresh independent read-only counter-audit**. This file changes no
approved architecture bytes and authorizes no implementation, task generation,
model/tokenizer call, LoRA fit, external deliberation, benchmark, or GPU use.

## Exact disposition

**REVISE, THEN ACCEPT THE FIVE-SERVICE COMMON-`ACTIVE_TEXT` TOPOLOGY FOR A
NARROW CLAIM. Do not accept the current gate verbatim.**

The proposed repair correctly identifies a blocking omission: raw RAG, an
unspecified file interface, and a terminal carrier assay cannot support a
claim against strong agent memory. Giving one frozen active-text mechanism to
all five deployment services is a fair and unusually strict way to ask whether
personal parametric writes add value *after* a strong textual adaptation path
is already available. `P1-P0` is the minimal controlled comparison for that
question. It does not require a sixth longitudinal service, an exact
ReasoningBank/ReMem reproduction, or a full MemoPilot training run.

As written, however, the repair overstates what that contrast identifies,
calls an externally adapting system an ordinary non-learning agent, validates
the retriever more strongly than the updater, leaves updater inputs and dense
retrieval underbound, and omits material resource terms. The bounded
LEAFE-style paragraph also asserts a rehearsal match that the current plan
does not contain. These are blocking byte repairs for a strong-memory claim,
not reasons to discard the topology.

## What the common layer does and does not identify

### Fair total-effect interpretation

Let `M_c(t)` denote service `c`'s active-text state. The mechanism is frozen
across cells, but its *content is post-treatment*:

```text
parenting / deployed LoRA
    -> thoughts and actions
    -> public outcomes and trace
    -> ACTIVE_TEXT update
    -> later actions.
```

Consequently,

```text
C_active = gAUC(P1) - gAUC(P0)
```

is the total effect of enabling deployment LoRA writes in a parented agent
that also has the common active-text mechanism. It includes the legitimate
closed-loop path in which LoRA changes experience, experience changes the text
store, and the store changes later behavior. That is aligned with the stated
flywheel question.

It is **not** a carrier-only comparison between LoRA and identical textual
memory, because `M_P1(t)` and `M_P0(t)` can diverge after the first different
action. Do not match, regress on, stratify by, or exclude roots based on
post-treatment store content or updater yield; doing so would condition on a
mediator and can create selection/collider bias. Store divergence is an
endpoint/mechanism trace, never an eligibility variable.

Rename `C_text` to `C_active`. Permit only:

> Periodic personal parametric writes added at least the registered margin to
> a parented agent already equipped with the same frozen active-text update
> and retrieval mechanism.

Do not infer that LoRA replaced textual memory, beat it at equal stored bytes,
or was the sole carrier. Adapter-off with the frozen `P1` text snapshot is a
local necessity diagnostic; a separately presealed same-history/store swap is
needed for a carrier-only attribution sentence.

### “Ordinary agent” semantic conflict

`R0` has frozen *parameters* but an evolving playbook produced by 96 model
calls over its life. It is therefore not a never-learning agent and not a raw
agent system. It is a **frozen-parameter active-memory agent**. Calling its
actor weights “raw” is accurate; calling the complete system “raw,”
“non-learning,” or the “never-learning twin” is not.

There are exactly two honest options:

1. **Minimal, recommended:** retain five services; call `R0` the
   `FROZEN_PARAMETER_ACTIVE_TEXT` reference and describe the public pair as a
   parented parametric learner versus a frozen-parameter active-memory agent.
   This is stricter than a raw-loop comparison and preserves equal deployment
   affordances.
2. If the paper or user insists on the literal phrase “ordinary never-learning
   agent,” add a sixth raw service with the same actor/tools/files/raw-ledger
   search but no model-generated text updates. A sixth service is required for
   that *semantic claim*, not for the strong-memory causal claim.

Do not silently keep five services while using both meanings. The user's
one-parent -> one-child -> parent deletion binding remains intact either way;
independent roots are replications, not a classroom or cohort.

## Updater leakage and second-intelligence risk

The pinned adapter-free child-base updater is not a parent and does not violate
parent deletion merely by existing. It is nevertheless a second inference
role inside deployment. The paper must render it as a common baseline
affordance, not part of DREAM or SLEEP, and must not credit its abstractions to
the life-LoRA.

Replace “over only that service's public trace and current store” with a closed
visibility manifest. The updater may receive only:

- that service's already-public deployment assistant messages, native actions,
  public outcomes, clock, and program-local score events through the current
  program;
- deterministic retrievals from that same service's prior raw ledger and
  playbook; and
- its own immediately preceding schema-valid `REFLECT` object for `CURATE`.

It must never receive parent outputs, childhood/nursery material, rehearsal or
anchor rows, admission/writer decisions, adapter parameters or logits, probe
traffic, future events, other services/roots, hidden compiler state, offline
truth labels, reporter output, or semantic reviewer judgments. Every input
event ID and rendered byte range must be receipted. Malformed updates remain
in the audit ledger and cannot cause root exclusion or replacement.

The store may be unbounded on disk, but neither updater call may read an
unbounded serialization. Before exact architecture ratification, bind:

- maximum rendered input tokens separately for `REFLECT` and `CURATE`;
- deterministic selection/order/truncation rules for the current trace and
  prior records;
- behavior when a complete required record cannot fit; and
- a no-whole-store fallback once the playbook exceeds the input cap.

Without these bytes the system is neither reproducible nor resource bounded.

## Retrieval is still underdefined

“Deterministic hybrid lexical+dense” is not a method. Bind the exact lexical
scorer and tokenizer, embedding model/revision and normalization, index
library/version, fusion equation and weights, query construction, one-hop
expansion order, tie breaker, duplicate handling, complete-record packing, and
the empty/no-hit behavior. Dense embedding calls and index rebuilds must be
receipted even if they are CPU-only. All choices freeze on development before
spending roots.

The proposed read cap—four complete records and 1,024 returned tokens per
ordinary continuation—is a legitimate named envelope. It is not a matched
memory-capacity result: textual state and index bytes are unbounded while LoRA
rank is fixed. Report a performance/resource frontier; do not say equal
memory, equal compute, or universal superiority.

## The strength gate currently tests the reader, not the writer

The three proposed checks can all pass with a useless updater: target-record
recall and direct-injection parity test retrieval/use, while an
**oracle-inserted** playbook bypasses `REFLECT` and `CURATE`. Add an independent
write/maintenance gate on disjoint development fixtures.

Minimum exact gate:

1. **Write/maintenance:** on 100 presealed public-trace update cases spanning
   add, support, contradiction, scope narrowing, link, and supersession, the
   actual two-call updater must achieve at least `.95` evidence-entailment
   precision, `.85` macro-F1 over the required delta/status operation, `.80`
   recall of prospectively marked reusable records, and 100% citation/source
   existence. Offline development truth scores this once outputs are sealed
   and never returns a correction to the updater.
2. **Read/use:** retain `>=.95` recall@4 and 100% returned-citation validity,
   but evaluate records created by the actual updater as well as oracle
   records.
3. **End-to-end strength:** on 24 target-blind development programs, the
   actual updater-produced `ACTIVE_TEXT` must beat the same actor with only
   append-only raw-ledger search by at least the registered `.05` task-value
   margin; retrieved active text must remain within `.05` of directly
   injecting the same updater-produced relevant records.
4. **Headroom:** retain the oracle-playbook versus empty-store `.05` check to
   show the environment can reward memory at all.

If any fails, repair only on development or report `ACTIVE_TEXT_NOT_STRONG`.
Do not tune on scientific roots, drop hard roots, weaken the read cap after
seeing results, or substitute a named-method claim.

This gate is intentionally functional rather than genealogical. ACE's
official method uses generator/reflector/curator roles and incremental
playbook updates; ReMem is an action--think--memory-refine pipeline;
ReasoningBank distills successful and failed experience into retrieved
reasoning memories. A two-call frozen updater may be a credible local
competitor after the gate, but only under the name
`ACTIVE_TEXT_FIXED`, “ACE/ReMem-style.” Exact reproduction becomes mandatory
only if the manuscript says it beats ACE, ReMem, ReasoningBank, or MemoPilot.
If `ACTIVE_TEXT_FIXED` cannot pass development, adapting one official
implementation is the next repair; it is not a sixth confirmatory service by
default.

Primary sources supporting this boundary:

- ACE: <https://arxiv.org/abs/2510.04618> and
  <https://github.com/ace-agent/ace>;
- Evo-Memory/ReMem: <https://arxiv.org/abs/2511.20857>;
- ReasoningBank: <https://arxiv.org/abs/2509.25140>;
- MemoPilot: <https://arxiv.org/abs/2606.08656>.

## Compute matching and causal language

Common `ACTIVE_TEXT` removes differential updater *availability*, not total
compute differences. `P1` additionally pays for three deployment fits; `P0`
does not. This is a valid system comparison, but not equal-compute evidence.
Do not burn dummy GPU time. Report:

- task value versus generated update tokens;
- task value versus updater plus LoRA training FLOPs/occupied GPU time;
- task value versus total actor+retrieval input tokens; and
- total persistent bytes for text, index, ledger, and adapter separately.

The updater's frozen greedy policy must be byte-identical across cells, but its
inputs and outputs should differ on-policy. Common counter keys apply only to
equivalent opportunities; do not force identical updater output after traces
diverge.

The hierarchy should read:

```text
D        = parenting-by-deployment-write interaction       # primary causality
C_active = gAUC(P1) - gAUC(P0)                             # strong-memory total effect
C_public = gAUC(P1) - gAUC(R0)                             # full package, descriptive/secondary
```

Sequential testing `D -> C_active -> C_public` is coherent. `C_public` does
not isolate parenting, LoRA, or memory and must never be described as doing so.
The blinded variance rule should include every contrast that will carry a
powered superiority claim, but failure of `C_public` precision must not erase
a valid `D` or `C_active` result; it only removes the public joint-superiority
rung. Publish the full hierarchy rather than converting all lower rungs to a
global null.

## LEAFE-style terminal control needs two corrections

The staged terminal control is useful only if the paper claims periodic
writes beat a batch reflective writer. It is not mandatory for the active-text
claim and should remain deferred until `D` and `C_active` artifacts are
immutable.

First, current `P1` has **20 fixed native anchor positions**, not “20%
successful-behavior rehearsal.” Delete the claimed equality. Bind the terminal
writer to the same 320-position geometry with:

- the same 24 childhood slots and 20 fixed anchors;
- 48 registered failure/recovery branch slots;
- three deterministic common rehearsal fills occupying the deployment DREAM
  slots; and
- deterministic rehearsal fills for any failed branch slot.

If a 20%-successful-rollout LEAFE feature is retained, label it an intentional
data-mixture difference and report its tokens; do not call it matched to `P1`.

Second, `P1` and `LEAFE_STYLE_FINAL` learn from different on-policy histories
and the latter receives counterfactual rollback actions. Therefore `C_batch`
is a comparison of two complete bounded systems, not a causal estimate of
periodic-versus-terminal timing alone. A schedule-only causal claim would need
the same frozen source history/rows passed to both writers, which is a separate
common-deck assay.

The branch resource line is arithmetically correct only if “1,024 probe
tokens” means the aggregate ceiling across each probe's eight calls. Write
that explicitly. Also receipt the 48 rollback actions/environment dispatches;
they are extra information-gathering opportunities even though no extra
48-program life is run.

## Resource audit

The stated output-call arithmetic is internally correct under its assumptions:

```text
ACTIVE_TEXT:       480 calls, 215,040 output tokens/root
LEAFE_STYLE_FINAL: 160 calls,  45,056 output tokens/root
combined:        5,451 calls, 1,017,600 output tokens, 13 fits/root
N=20 route:    141,726 calls, 26,457,600 output tokens, 356 fits
N=32 route:    207,138 calls, 38,668,800 output tokens, 512 fits
```

It is not yet a complete resource envelope. At the maximum read allowance,
automatic pre-continuation retrieval alone can inject up to:

```text
deployment wake: 5 * 48 * 12 * 1,024 = 2,949,120 input tokens/root
checkpoint probes: 5 * 4 * 8 * 8 * 1,024 = 1,310,720 input tokens/root
total maximum returned text = 4,259,840 input tokens/root
```

This is a conservative ceiling because the plan says “before each ordinary
actor continuation”; if 1,024 is instead aggregate per program/probe, change
the read contract and arithmetic together. Add updater input-token ceilings,
embedding/index work, store serialization, retrieval latency, LEAFE rollback
dispatches, development strength-gate cost, and the 10,000-sequence saturation
reference to the resource manifest. The latter two may remain outside
scientific-root totals but must have hard ceilings before execution.

## Saturation ruling

The proposed saturation language is appropriately conditional and does not
block the parenting interaction. Keep the equivalence requirement, headroom
reference, positive `P1` last-era growth, and positive last-era
difference-in-differences. Add exact bytes for the repeated-measures root-level
estimator, max-t resampling unit/seed/replicates, multiplicity family, missing
root rule, and whether all eight probe programs are paired across cuts.

Even if all conditions pass, name the comparator and envelope every time:
`P0+ACTIVE_TEXT_FIXED`, 48 programs, the bound updater/read budget, and this
CompilerGym distribution. It is a local plateau, never intrinsic memory
saturation. With at most 32 roots and eight probes, equivalence may remain too
wide; the already-proposed outcome—omit the word and report curves/resource
frontiers—is the correct one and must not trigger an unplanned root increase.

## Minimal proposal-byte changes

Before adding this advisory to deliberation, minimally patch the strong-memory
proposal as follows:

1. Rename `C_text` to `C_active` and insert the total-effect/mediator language
   above; forbid carrier-replacement claims.
2. Replace every complete-system `R0` occurrence of “raw,” “non-learning,” or
   “never-learning” with `frozen-parameter active-memory`, while preserving
   “raw pinned actor weights.” If that wording is unacceptable, explicitly
   add and resource a sixth raw service instead.
3. Add the closed updater visibility manifest, bounded updater-input selection,
   and fully pinned hybrid-retrieval bytes.
4. Replace the strength gate with separate write/maintenance, read/use,
   end-to-end actual-updater, and oracle-headroom gates.
5. Add the resource omissions and clarify whether 1,024 retrieval/probe tokens
   are per continuation or aggregate.
6. Replace the false “20% rehearsal as P1” match with the exact 320-position
   slot mapping; narrow `C_batch` to a complete-system comparison.
7. State that `C_public` imprecision removes only that claim rung, not valid
   lower hierarchical results; bind the saturation estimator bytes.

No other topology change is necessary. In particular, do **not** add a
classroom, cohort, shared store, cross-child data, parent after deletion, or
teacher ensemble.

## Final ruling

The central repair is scientifically sound: a common strong active-text layer
makes `P1-P0` harder to win and answers the relevant reviewer objection with
minimal extra services. It is sufficient for the bounded claim that deployed
parametric consolidation adds value beyond a strong prompted textual-memory
mechanism. It is not sufficient for parametric-versus-text carrier replacement,
equal-compute superiority, universal memory superiority, or a literal
never-learning-agent contrast.

**Advance only after the seven byte repairs above enter the architecture
deliberation and exact human ratification.** Exact named-method reproduction
and a sixth service are conditional, not mandatory. This advisory itself
authorizes neither implementation nor execution.
