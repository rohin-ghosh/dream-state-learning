## Pair target, loss, input and output

- **Within-contest ordering is empirical `mean`, not `q`.** `preprocess_dpo` samples pairs within one contest's ranking file and requires `mean_chosen - mean_rejected > 3 * sqrt(precision_chosen**2 + precision_rejected**2)`. It stores the selected caption strings as `chosen` / `rejected`, separately from the scene `prompt`. No `q` field or q-based target is used in this path. `precision` is the literal column name; its exact statistical definition was not independently checked through dataset records. The paper describes three-standard-deviation separation. Neither scalar means nor a rating histogram become regression targets in the reward-training tensors. [G1, P1]
- **Pair-loss sign favors the higher-mean caption.** The project uses `CustomRewardTrainer(RewardTrainer)` without overriding `compute_loss`; the paper describes Bradley–Terry reward learning. The pinned TRL v0.8.6 reference implements `mean(-logsigmoid(r_chosen - r_rejected))` when no margin is provided. The authors' preprocessing supplies no margin tensor: the three-precision threshold filters pairs; it is not itself a loss margin. The actual training TRL version is unpinned/unverified, so the reference implementation is corroboration, not a recovered training environment. [G2, P1, L1]
- **Training input is caption-only in the inspected implementation.** `humor_reward_modeling.py` tokenizes only `pair['chosen']` and `pair['rejected']`, with truncation/padding to 512 tokens. The separately stored scene prompt is never concatenated there. Dataset assembly saves that output directly. This establishes the published code path, **not** what uninspected checkpoint bytes were actually trained on. [G1, G2]
- **Published BoN/PPO inference instead prepends textual scene context.** BoN scores `prompt + caption`; the prompt fields are `scene`, `description`, `uncanny description`, `entities`, then the caption slot. PPO similarly scores query + response. There is no pixel/image encoder in this reward architecture. This is a concrete published training/inference conditioning discrepancy; do not claim a verified scene-conditioned trained reward model, or silently fix/retrain it in this sidecar. [G1, G3]
- **Output is one unbounded scalar per input, not a rating distribution.** Training/scoring request `num_labels=1`; the HF config has one label and the tensor index contains `score.weight`. BoN explicitly sets `function_to_apply='none'`: `return_all_scores=True` still yields a singleton score, not three class probabilities. A sigmoid of two score differences is a Bradley–Terry pair probability under that model, not a calibrated human mean, `q`, or the distribution over 1/2/3 ratings. [G2, G3, H1, L1/L2]

## Architecture, packaging and loadability

For the **linked initialization only**, the pinned JSON specifies native `MistralForSequenceClassification`, 32 layers, hidden size 4096, intermediate size 14336, 32 attention heads / 8 KV heads, vocabulary 32001, BF16, context configuration 32768, and `transformers_version='4.38.1'`. The pinned Transformers v4.38.1 source contains that native class with a bias-free `score` head. There is no `auto_map` or custom Python model code among the listed HF files. `trust_remote_code=False` is therefore the appropriate proposed first attempt; the authors' training flag defaulting to `True` is not evidence that remote code is required. [H1, L2]

Tokenizer metadata names `LlamaTokenizer`, BOS 1 / EOS 2 / dedicated PAD 32000, `model_max_length=4096`, and a Mistral `[INST]` chat template. Both `tokenizer.json` and SentencePiece `tokenizer.model` are advertised; neither vocabulary file was fetched. A compatible fast tokenizer can use the JSON, while a slow-tokenizer path needs SentencePiece. Native Transformers/PyTorch, a supported tokenizer stack and safetensors support are required; GPU kernels, bitsandbytes, TRL and the custom trainer are not inherently required for inference on this full initialization. Applying the chat template is not the authors' caption-only training path. [H1]

The model API advertises **7,110,668,288 BF16 parameters**, three safetensors shards (14,221,370,376 bytes including overhead), and an index whose tensor payload totals 14,221,336,576 bytes. Shard SHA-256 identities and sizes are preserved from server LFS metadata; **weight bytes were neither downloaded nor independently hashed**. Config/index/tokenizer-metadata response bytes were checked against their Git blob IDs. This is a plausible standard local-load package, not proof of a successful forward pass, complete local cache, or intact tensor contents. [H1]

The authors' training defaults use LoRA (`r=16`, alpha 16, `SEQ_CLS`), but the adapted release could be an adapter or a merged model: neither was inspected. The declared `modules_to_save=['scores']` differs from native `score.weight`; PEFT may preserve the score head automatically, so flag this as a required serialization check, **not** a diagnosed broken checkpoint. Training rewrites PAD to EOS unless a new pad is requested; BoN also takes its tokenizer from a separately supplied `--model_name`. The actual release must bind base revision, tokenizer, embedding size, saved head and pad/pooling behavior together. [G2, G3, H1, L2]

Exact-revision, filename-only checks found **zero matching snapshot directories** for the initialization and its upstream LM in the standard HF cache; no cache override was configured. No other model caches, private work directories, cached file contents or home-wide inventory were inspected. This does not rule out differently located copies or an unidentified adapted checkpoint. [C1]

## License and contamination boundaries

- The authors' **source repository** has Apache-2.0; the underlying Mistral-v0.2 model card also declares Apache-2.0. The inspected generic reward model card has empty license metadata and no listed license file; a separate adapted-checkpoint license was not established. Do not equate code/upstream licensing with verified license terms for every derivative weight or benchmark data artifact. [G4, H1/H2]
- The paper reports a corpus of **365 contests in 530–895**. Fine-tuning uses available contests in **530–890**, with 47 test + 44 validation contests from the earlier benchmark forming its 91-contest evaluation split; the rest of the available contests form training. It also selects the reward checkpoint using holdout reward evaluation. Thus direct training overlap and checkpoint-selection exposure must both be considered. This is an aggregate range, **not** a recovered exact training-contest manifest. [P1]
- Any comparator benchmark intersecting that pool needs a separately permitted contest-ID/provenance audit before independence claims. No current held/FINAL/R176 artifacts or evaluation rows were accessed, so no intersection was computed. Generic reward pretraining additionally uses a broad preference mixture; its card is not an exhaustive decontamination certificate. **Public availability does not establish an uncontaminated, independent or unrestricted benchmark.** [P1, H1]
