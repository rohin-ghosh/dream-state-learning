# V6 blocker resolution: fresh-from-birth SLEEP and closed one-way plumbing

Date: 2026-09-09

Status: successor-proposal input only. No implementation, model/tokenizer
execution, data or benchmark generation, writer/adapter/checkpoint work,
GPU/resource use, external scientific execution, claim, publication, push, or
release is authorized.

The learner remains simple:

- **THINK** is the child's continuous thought, action, and public-outcome loop.
- **DREAM** is waking context management only.
- **SLEEP** organizes grounded child-authored experience and writes a personal
  LoRA.
- An optional one-time, target-blind **birth bootstrap** may teach general
  feedback-to-action habits before parenting. It is schooling, not personal
  SLEEP.

This document repairs seven exact-proposal defects in v5. It adds no cognitive
organ.

## 1. Personal SLEEP always rebuilds from the immutable birth

Remove prior-active-weight access from the E4 personal writer. At every SLEEP:

1. start a new zero-effective-delta personal adapter on the immutable assigned
   birth;
2. train it on the full eligible cumulative child-life corpus under the frozen
   replay/dose rule;
3. stage the result as a candidate; and
4. let E5, not E4, compare the prior active child with the candidate.

Prior weights cannot condition corpus construction, initialization, sampling,
dose, gradients, or candidate bytes. A required fixture mutates prior active
weights while holding birth, eligible corpus, writer contract, and seed fixed;
the candidate must remain byte-identical.

## 2. The compiler may enrich expression, not invent cognition

Every target clause has one or more exact child-authored proposition IDs plus
public action/outcome support IDs. The compiler may:

- select supported child propositions;
- partition, order, deduplicate, and replay them;
- place two already-authored propositions beside each other as a contrast; and
- render meaning-preserving paraphrases and retrieval/use views.

It may not introduce a new predicate, argument, relation, scope, causal claim,
temporal claim, confidence claim, or generalization. A generalized proposition
is eligible only when the child previously stated that proposition and its
declared evidence threshold is satisfied. Grounded premises do not authorize a
compiler-synthesized conclusion. Bidirectional semantic audits and adversarial
clause fixtures police this boundary; disputed clauses fail closed.

Parent words remain in waking context and the restricted audit ledger only.
They become neither SLEEP conditioning nor targets. The child may independently
restate and enact a repeated lesson; only its later supported child-authored
experience follows the ordinary rule above.

## 3. Exact capability registry, not names plus prose

The successor binds a machine-readable registry. Every capability entry names:

- capability ID and version;
- exact operation: `READ`, `WRITE`, `APPEND`, `DEREFERENCE`,
  `BIND_EQUALITY`, `ADVANCE`, or `TRANSFER_OPAQUE`;
- artifact class and canonical request/result schemas;
- sole issuer, producer, and allowed consumer set;
- namespace, invocation epoch, cardinality, and single-/multi-use rule;
- artifact lifetime separately from handle lifetime;
- seal, attenuation, revocation, expiry, and replay behavior; and
- constant-shape success/failure results that expose no content-derived count,
  ID, hash, ordering, timing, cache, filename, or error side channel.

The visibility product is generated from this registry. An undeclared method
does not exist. There is no generic `visible` or `derived_only` authority beyond
the registered operation.

## 4. Persistent artifacts cross epochs; capabilities do not

An immutable artifact may persist. A capability handle may not silently cross
an epoch.

At each declared producer-to-consumer boundary, a model-free epoch bridge:

1. seals the producer artifact and closes the producer handle;
2. checks the registered artifact class and root equality;
3. issues a fresh attenuated per-consumer handle containing a new invocation
   ID, exact operation, exact artifact class/root, and expiry; and
4. records a fixed-schema transition receipt.

Copied, replayed, widened, wrong-consumer, revoked, and stale handles all return
the same constant-shape failure. E2/E3/E4/E5/E7/E8 reuse is replaced by distinct
consumer-epoch capabilities. Equality-only tokens never dereference content.

## 5. Birth construction receives an explicit frozen contract

Add an E1 read capability whose immutable artifact binds the exact bootstrap
writer, response mask, tokenizer, merge equation, numeric dtype, serializer,
toolchain, model root, seed, truncation, and receipt schemas. The birth writer
has no ambient configuration or network fallback. Any environment-dependent or
unbound value fails before birth work.

## 6. Close every receipt and attestation producer

Every readable object has exactly one registered producer or one exact external
source and an explicit close-and-reissue transition. In particular:

- build-time dependency manifests and dispatcher manifests come from a
  model-free static manifest sealer;
- taint receipts come from the registered support/compiler capability monitor;
- lineage transaction receipts come from the candidate and promotion
  transaction stages;
- preservation evidence comes from the E5 evaluator;
- blindness and lineage auditors each emit both a detailed quarantined finding
  and a fixed-size pass/fail attestation;
- the authority verifier reads only those narrow attestations and an exact
  external human authorization artifact; and
- no audit input or output contains hidden scientific truth, score, report,
  child text, parent text, or candidate semantic content.

The complete stage-capability product includes the producers, epoch bridges,
and consumers. No ambient sidecar is permitted.

## 7. Bind opaque transfer to a complete release tuple

`TRANSFER_OPAQUE` is a registered copy-only operation: it cannot inspect content
or branch on it. Any later authorization and verdict bind the exact tuple:

`(artifact_root, artifact_class, destination_identity, transfer_operation,
protocol, requested_scope, nonce, expiry, one_shot_idempotency_key)`.

The controller may transfer only that tuple once and emits a receipt echoing it.
A bare root is insufficient. The scientific architecture itself authorizes no
release; a future release requires its own exact human artifact.

## 8. Remove circular gate ordering with two authority layers

The successor binds a machine-readable action-to-prerequisite DAG.

### G0: model-free gate harness

A first, narrowly scoped human ratification may authorize only implementation
of the registry parser, fake artifacts, fake dispatchers, epoch bridge, receipt
validator, action DAG, and deterministic fault fixtures. It authorizes no real
model/tokenizer, treatment data, benchmark generator, writer, adapter, merge,
checkpoint, candidate, evaluation, GPU/resource, external-science, claim, push,
publication, or release action.

Static completeness and fake-transaction tests run in G0. Thus the gate does
not depend on a protected domain action to create its own prerequisite.

### G1 and later: separately bound domain scopes

Only after G0 passes may a new exact human authorization permit named domain
implementation. Each later first affected action is separately mapped to the
receipts that must already exist. Dynamic writer, tokenizer, data, candidate,
exam, GPU, claim, and release gates occur before their own corresponding action,
not before the fixture code needed to test the gate.

Missing, failed, stale, wrong-root, wrong-scope, expired, replayed, or cyclic
prerequisites fail closed.

## 9. Downstream contracts remain downstream

After a successor architecture passes, separate exact packets must still freeze
implementation schemas and transactions; bootstrap sources/splits and semantic
audits; solo-resource controls; writer factorial and dose; preservation rules;
support resolver; replay closure/filler; endpoints, power, intervals,
multiplicity, missingness, safety comparators, and stopping; GPU allocation; and
claim/release scope. The architecture proposal does not pretend these results
already exist.

## 10. Scientific meaning remains unchanged

The bootstrap is successful only if it speeds learning, not merely if it makes
the child recite a ritual:

- `Delta_R`: immediate selective use of correct new process advice versus none,
  irrelevant, and wrong advice in disposable same-state clones;
- `Delta_F`: faster learning under a fixed repeated curriculum plus personal
  SLEEP, measured across the 32-lesson curve rather than only at the end; and
- `Delta_E`: the separately labeled practical adaptive-parent-plus-child-plus-
  SLEEP package.

The core factorial remains birth `{M0, direct-solution control, teachability}` ×
parent `{absent, fixed}` for mechanism, with adaptive parenting reported
separately. All downstream evaluation begins from empty active context, uses
fresh executors, and cannot feed the continuing child.
