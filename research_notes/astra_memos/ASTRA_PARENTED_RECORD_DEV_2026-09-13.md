# Fixed process coaching → own-record write → parent-free DEV

Prospective protocol, September13 09:44UTC. CPU implementation in progress;
not launched. Main adopts this minimal variant of the recovered RuleGame
parenting design, independently of the authored contrastive-dose experiment.
Simple hygiene applies; no final-paper C11 guard is introduced here.

## Question and inference boundary

Does a fixed process reminder improve the child's source-faithful records and,
after writing only those records into its own adapter, its parent-free record
formation on fresh DEV situations? Chosen competency: preserving the actual
pre-action prediction separately from the returned observation and deriving
their relation. This responds to SEQ149/153/154/155 prior-field failures.
It tests fixed-guidance amortization, not adaptive-parent intelligence, action
grammar learning, general learning efficiency, a stable substrate or H1/H2.
Coaching is author-supplied process supervision, not a generated teacher answer.

## Three matched learner pairs

Start from original Level1 perception adapters for seeds0/1/2, never previous
memory descendants or only the seed that passed the lower-rate screen.
Within each seed, P=process coaching and N=active-neutral contact fork identical
tensors and settings. No mutable model/optimizer/history is shared across arms.
Both receive contact and a child restatement; N is not a no-contact control.
No parent model calls are needed. Exact contact strings:

P: Keep the prediction you stated before acting separate from the observation
returned afterward. Record that prior unchanged; do not replace it with the
outcome or with null. Derive the relation by comparing those two values. If no
prediction was stated, record null and unavailable.

N: This part of the session is complete. Continue with the next scheduled
exercises using the task instructions. You may briefly acknowledge this
message before proceeding.

Two fixed rounds per arm. Each round: one fresh two-turn pre episode, the
fixed contact, one unrestricted child restatement, four fresh two-turn apply
episodes. Pre records/restatement/contact are audit-only. Only the sixteen
apply opportunities per arm can supply sleep targets. No replacement tasks,
regeneration for compliance, successful-seed selection or extra contacts.
The contact/restatement block is temporary apply context, not part of sleep.
Episode-local action histories reset normally. Same IDs/order/caps and the
same frozen comma-containing ACT example across arms/seeds and held tasks.
Do not repair malformed actions. Scaffolding is held fixed, not internalized.

Use existing RuleGame public interactions and strict action/record parsing.
Record real child actions and real environment responses, not oracle actions.
No hidden rule, eligibility score, sibling-arm material or held result enters
child/contact context. Primary effects allow actions and experiences to differ;
same initial tasks do not identify same-experience conversion effects.

## Source admission and write

Preserve every raw response and refusal. Admit only the child's unchanged raw
apply record when the existing source judge verifies all required fields,
schema/completion and provenance. Do not normalize noncanonical valid JSON,
fill missing fields, include model-written parent/restatement prose, or copy
expected-answer fields into targets. Report all16opportunities, reached
executions, actual record calls and admitted records, not selected successes.

Each arm writes its own admitted records with the validated warm-start LoRA
writer: rank8/alpha16/dropout.05, LR3e-5, fresh optimizer, eight passes, batch1,
same learner seed and deterministic ordering recipe, original masks/EOS.
Same dose policy per admitted record; differences in admitted count and tokens
are intended material-yield effects and must be reported, not called equal
total compute. No additional own-source replay in this version.
If n=0, record NO_WRITE and retain original tensors; do not forge a fit/LR0
stage. n<=16 gives<=128updates/arm,<=768across all six fits. Other primitives
and parameters remain frozen. No early stopping or dose adaptation from scores.

## Parent removal, held assessment and controls

After write, reload each saved adapter in a fresh process. Remove contact,
restatement, apply transcripts, retrieval state and temporary caches. Retain
only assigned learned weights and fixed execution/record instructions.
Evaluate P,N and the original no-update parent on the same eight fresh DEV
held episodes, two turns each. Original parent is a genuine no-update
checkpoint, not a newly trained zero-LR adapter. At most32calls/state.
Primary metric: source-faithful eligible held records /16opportunities.
Also report P-minus-N, gains relative to initial parent, fields, canonical
format, actual executions, raw failures, turn splits, source novelty and costs.
Report all three learner pairs independently; repeated turns are correlated.

Evaluate the original48held perception and12canary items on each new descendant;
import the pinned original-parent baseline for these OLD retention panels as
historical/noncontemporaneous rather than rerunning completed controls.
Itemwise losses remain visible. These panels have informed repair selection
and are exploratory. No selected comparison gains fresh-confirmation status.

Prepare disjoint DEV-pre/apply, DEV-held, CONF-pre/apply and CONF-held ID
namespaces; source-check against prior exposed task IDs. Do not run or inspect
CONF responses in this DEV block. Fresh IDs do not ensure unseen rule classes,
action triples or base-model knowledge. Freeze exact bytes/manifests before
launch; no search for favorable rule/ID assignments. A later selected CONF
run starts from original parents and generates new own material, not selected
DEV records. Reused learner seeds do not become six independent learners.
