## 2. Common byte and integer primitives

The v3 master bytes are exactly:

```text
M-COMBINE-4/STAGE2A/V3/2026-09-13
```

`NUL` is one byte `0x00`. `U32(n)` is exactly four bytes, unsigned big-endian,
and is defined only for `0 <= n < 2^32`. `SHA256(b)` is the 32 digest bytes,
not hexadecimal text. Every hexadecimal digest in this memo is lowercase.

Define once for every adapter, dropout, and decode seed:

```text
low64(b) = unsigned_big_endian_integer(SHA256(b)[24:32])
```

Thus `low64` uses the final eight digest bytes and returns an integer in
`0..2^64-1`. No platform byte order, signed conversion, first-eight-byte
interpretation, modulo, or decimal-string hashing is allowed.

Canonical JSON, called `CJSON` below, is UTF-8 encoding of Python-equivalent
`json.dumps(value, sort_keys=True, separators=(",",":"), ensure_ascii=True)`
with no terminal LF. Values are limited to objects with unique string keys,
arrays, strings, integers, booleans, and null; floats are forbidden. Sort keys
by Unicode code point, which equals raw ASCII order for every bound key here.
Reject duplicate keys, non-ASCII source strings, invalid UTF-8, CR, NUL, NaN,
Infinity, and negative zero before canonicalization.

### 3.2 Allocation and collision rules

For each materialized domain and kind, let `ROLE_LIST` be the raw-ASCII-sorted
role keys constructed below. Its bytes are the keys joined by LF with no final
LF; the empty list is zero bytes. Allocate exactly `len(ROLE_LIST)` candidates:

```text
digest = SHA256(master || NUL || domain || NUL || kind || NUL || U32(serial))
token  = kind_prefix || RFC4648_BASE32(digest)[0:12]
serial = 0..len(ROLE_LIST)-1
```

RFC-4648 base32 is uppercase, padded conventionally before taking the first
12 characters; padding cannot occur in that prefix. Sort tokens by
`(SHA256(master || NUL || domain || NUL || "pool-order" || NUL || token),
token_bytes)`. Sort role keys by
`(SHA256(master || NUL || domain || NUL || "role-order" || NUL || role_key),
role_key_bytes)`. Zip them.

The build fails, without skip/retry/reseed, on: a duplicate candidate in one
kind; the same complete token in two domains; an all-`A` suffix; a digest tie
without applying the stated raw-byte tie break; a role-list count/hash
mismatch; a missing/extra role; or a pinned display-position collision.
Different kinds are separated by their prefixes. The two unmaterialized
domains `confirmation_reserved` and `writer_reserved` retain v2's exactly
4,096 serials per kind; they have sealed pools but no role list or semantics.

## 4. Finite rows, ownership, registries, and worlds

### 4.1 Directory and ordinary relation construction

An INDEX registry exists only for every `Z` state named in section 3.3. It
owns exactly 24 route rows, one per goal, and returns v2's exact `ROUTES`
wire. A goal, wrong-AT, predicted-only, or surprise state has no INDEX entry
unless it is literally in `Z`; an INDEX there returns `MISS`.

Every `z/JJ/useful/-/query` owns exactly one four-row EVENTS block. Candidate
component `c` is the rendered row index `0..3`; there is no second hidden row
permutation. Except for the relation/deep-swap target block below, let

```text
v = (3*j + state_ordinal(z) + skin) mod 4
```

and render:

```text
row v       AT z         FOR g_j
row v+1     AT z         FOR g_((j+1) mod 24)
row v+2     AT x_j       FOR g_j
row v+3     AT x_((j+1) mod 24) FOR g_((j+2) mod 24)
```

All row arithmetic is modulo four. State ordinals are: birth `s=0`,
`a_j=j+1`, `b_k=25+k`, `surp_m=81+m`; intervention `s=0`; chain `s=0`,
`h_k=100+k`, `w_k=108+k`. Each row uses the event, port, receipt, and RECOVER
query with the same `z/JJ` and candidate component. Thus a row's RECOVER
operand is always `z/JJ/recover/c/query` for an ordinary block or
`state/JJ/recover2_m/c/query` for a corrective block.

For a relation/deep-swap target block, let `u` be v2's exact value. Member m0
has:

```text
row u       AT z     FOR task_GOAL
row u+2     AT z     FOR decoy g_((j+1) mod 24)
row u+1     AT x_j   FOR task_GOAL
row u+3     AT x_((j+1) mod 24) FOR g_((j+2) mod 24)
```

Member m1 swaps only the two FOR fields at rendered rows `u` and `u+2`.
Event, port, receipt, RECOVER, AT, GOT, IDs, and row positions do not change.
In a reached cell both current-state rows GOT task GOAL. In an unresolved A
cell they GOT `a_j` and `a_((j+1) mod 24)` at rows `u` and `u+2`; in B they
GOT `b_(j mod 6)` and `b_((j+1) mod 6)`. This replaces any conflicting generic
destination rule.

Otherwise GOT/world is total:

- from birth `s`, a reached row with AT `s` GOT its FOR goal; an unresolved
  row GOT `a_k` or `b_(k mod 6)` for FOR goal `g_k`;
- from a birth `a` or `b` hub, a row with AT that hub GOT its FOR goal;
- from intervention `s`, a row with AT `s` GOT
  `h_((5*k+r) mod 8)` for FOR goal `g_k`;
- from chain `s`, it GOT `h_((5*k+r) mod 8)`; from chain predicted hub `h_q`,
  it GOT its FOR goal;
- from any registered birth/chain surprise corrective block, a row whose AT is
  that surprise state GOT its FOR goal;
- a row with AT `x_k` GOT `x_((k+3) mod 24)` in every domain.

Absent a declared mismatch or CHECK outcome intervention, the fixed world
edge `(AT,DID)` has destination GOT. Every event-row port is unique within its
world, so `(AT,DID)` has exactly one edge. No other world edge exists.

## 7. Canonical graph, hyperedge, core, and signature bytes

### 7.1 Typed graph construction

Vertex types are exactly `EVENT`, `GOAL`, `PORT`, `QUERY`, `RECEIPT`, and
`STATE`. A public node used as a GOAL and STATE creates two typed vertices.
ROUTE-row IDs are intentionally surface evidence, not graph vertices. Graph
edge labels and ordered incidence are exactly:

```text
INDEXES   tails [STATE,GOAL] heads [QUERY]
CONTAINS  tails [QUERY]      heads [EVENT]
FOR       tails [EVENT]      heads [GOAL]
AT        tails [EVENT]      heads [STATE]
DID       tails [EVENT]      heads [PORT]
GOT       tails [EVENT]      heads [STATE]
RECOVER   tails [EVENT]      heads [QUERY]
EVIDENCE  tails [EVENT]      heads [RECEIPT]
WORLD     tails [STATE,PORT] heads [STATE]
```

Each registered ROUTE row contributes INDEXES. Each row in a registered
relation/recovery block contributes CONTAINS and its six EVENT field edges.
Each fixed world transition contributes WORLD. An effective CHECK graph
replaces the designated base WORLD head with its intervention destination; it
does not contain both. Unregistered queries are vertices when allocated or
visible but own no CONTAINS edge. There are no implicit pair vertices or
ordinary binary substitutes for the two-tail hyperedges.

The `public_graph` for a decision contains the typed vertices and only edges
entailed by exact task facts, returned rows, and executed WORLD outcomes in
that prefix. The task GOAL has flag `GOAL`; latest CURRENT has `CURRENT`.
`typed_vertex_counts` counts this public graph only. The separate
`world_graph` contains the entire task world/store, including allocated
isolated vertices, and is evaluator custody. Rooted signatures use the
world_graph and root at the task oracle's first irreversible EVENT and its DID
PORT, flagged `ROOT_EVENT` and `ROOT_PORT`, regardless of decision phase.

### 7.2 Typed alias derivation and graph CJSON

For each graph vertex, take its allocator role key, remove the leading domain
and world components, join the remaining five components with `/`, and append
`#` plus the vertex type. That is its `local_owner_key`. If one node token has
both GOAL and STATE vertices, the suffix distinguishes them. No two vertices
of one type may have the same local owner key.

Within each type, sort vertices by raw-ASCII `local_owner_key` and number from
zero. Aliases are the following letter plus exactly four zero-padded decimal
digits: `E/G/P/Q/R/S` for EVENT/GOAL/PORT/QUERY/RECEIPT/STATE. More than 9,999
vertices of one type in a single world is invalid; no bound world approaches
it. `local_owner_key` and public IDs do not enter output JSON.

A vertex object is exactly
`{"alias":string,"flags":array,"type":string}`; flags are the applicable
subset of `CURRENT,GOAL,ROOT_EVENT,ROOT_PORT`, raw-ASCII sorted. An edge object
is exactly `{"heads":[aliases],"label":string,"tails":[aliases]}` with
incidence order from section 7.1. Sort vertices by alias bytes. Sort edges by
their individual CJSON bytes. The graph object is exactly
`{"edges":[...],"vertices":[...]}` and graph hash is:

```text
hex(SHA256("M2A-GRAPH-V3" || NUL || CJSON(graph)))
```

This deterministic typed-role canonicalization replaces v2's infeasible
unspecified permutation minimization. It ignores public identifiers while
remaining independently reproducible from the canonical role list.

PROSPECT, CHECK, CONTINUE, canary, each in the orders above. A separate dense

